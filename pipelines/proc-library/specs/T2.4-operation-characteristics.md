# T2.4 — Operation characteristics (reference economics)

Status: draft · Phase 2 · English (service doc)

## Purpose

Populate the T0.5 Decision 1 economics block on every operation of the
**Planning** pilot (`PLAN` + `SL_PLAN`) and fix the reference-value convention
used by the template. Everything here is a **reference value** for an SME
template — never a client figure (T0.6 Decision 1 criterion 2, T3.2).

## Decision 1 — attributes authored per operation

Per T0.5 Decision 1, each operation carries (in this order, after `КПЭ`):

| Key | Domain | Meaning |
|-----|--------|---------|
| `Критичность` | `high \| medium \| low` | impact if the step fails; defaults `medium` |
| `Периодичность` | `<cadence> ×<count>` | executions per cadence period |
| `Трудоёмкость` | `<number> ч` | labour hours per single execution |
| `Стоимость` | `<number> руб` | reference cost per single execution |

`decomposition` (from T2.2) stays; `Исполнитель` already carries the owner
(plan §T2.4 "owner").

## Decision 2 — cadence rule (`Периодичность`)

In the pilot the operation's **planning horizon is its execution cadence**:
`Периодичность` = `<Горизонт> ×1`. Rationale: the pilot decomposes each
subprocess into one pass of universal steps, and each operation's КПЭ confirms
the cadence (e.g. SL_PLAN-01-02-01 «Еженедельный анализ» → `week ×1`;
PLAN-03-01-05 «не реже 1 раза в квартал» → `quarter ×1`). A client refines the
count (`×N`) without changing the schema.

Cadence → executions per year (T0.5 D2): `shift` 3×365, `day` 365, `week` 52,
`month` 12, `quarter` 4, `year` 1, `event` explicit.

## Decision 3 — reference labour and cost

- `Трудоёмкость` is authored per operation from its nature (dedicated analysis
  4 ч, routine entry 0,25 ч, …), rounded to 0,25 ч.
- `Стоимость` = `Трудоёмкость × REF_RATE`, where **`REF_RATE = 1000 руб/ч`** is
  a single blended reference labour rate (placeholder; the client replaces it
  with its own rates in T3.2). Cost is therefore reproducible and never a client
  number.
- `Критичность`: `high` for control / bottleneck steps whose failure blocks the
  flow (data-completeness gate, requirement calculation, fact-vs-plan
  reconciliation, ABC/XYZ matrix, stock norms); `low` for pure entry / forwarding
  steps; `medium` otherwise.

`AnnualFund` (T2.5 FTE denominator) = **1700 ч** reference annual fund per FTE.

## Decision 4 — `decomposition` at the pilot

Every pilot operation is `ATOMIC` (T0.6 D2: universal steps fully specified in
the template). No pilot operation is a `DECOMPOSABLE` stub — the pilot
subprocesses are decomposed in full. T2.4 only confirms the attribute is present
and in domain.

## Decision 5 — ABC/XYZ seam de-duplication (§7.9)

T2.2/T2.3 carried a `POSSIBLE DUPLICATE` (§7.9): `PLAN-03-02-03` and
`SL_PLAN-01-03-02` had identical I/O signatures (`Сводка@Потребление` →
`КлассификацияABCXYZ@XYZ`). Per T0.1 D2 §3 (**PLAN-03 owns norms, SL_PLAN-01
owns replenishment**) the two classifications are genuinely distinct, so the
duplicate is resolved by disambiguating the **consumed input**, not by removing
a producer:

- `PLAN-03-02-03` keeps `Сводка@Потребление` (strategic statistics from
  PLAN-03-01-01);
- `SL_PLAN-01-03-02` consumes `Отчёт@ДвижениеЗапасов` (warehouse movement from
  SL_LOG-01-02-01), matching SL_PLAN-01-03-01.

The flow graph is updated: the `PLAN-03-01-01 → SL_PLAN-01-03-02` demand edge is
removed and `SL_LOG-01-02-01 → SL_PLAN-01-03-02` (movement report) added, so
§4.2 stays closed.
