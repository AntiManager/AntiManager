# T2.1 — Planning domain boundaries and shared entities

Status: draft · Phase 2 · English (service doc)

## Purpose

Fix the perimeter of the **Planning** pilot vertical (`PLAN` + `SL_PLAN`) and the
shared `Entity-State` types its operations exchange, so the flow graph (T2.3) can
be closed "within the instance" (ontology §4.2) and the enterprise-loop boundary
is explicit (plan §3). The pilot deliberately spans the production↔logistics seam
(PLAN ↔ SL_PLAN) to calibrate the cross-domain graph.

## Decision 1 — perimeter (sensor / actor)

Per T0.5 Decision 3, boundary operations are **sensors** (`|Входы|=0`,
`|Выходы|=1`, external source) and **actors** (`|Входы|=1`, `|Выходы|=0`,
external sink). The Planning vertical has this perimeter:

| Boundary | Op code | Direction | Entity | External counterparty |
|----------|---------|-----------|--------|-----------------------|
| sensor | `PLAN-01-01-01` | in | `ПроизводственныйЗаказ` | УПЛ / отдел продаж (order intake) |
| sensor | `SL_PLAN-02-01-01` | in | `ЗаданиеНаПеревозку` | отдел продаж (1С:ERP transport request) |
| actor | `PLAN-02-03-04` | out | `Отчёт@Утверждён` | УПЛ / руководство (report out) |

Everything else in the two files is an **internal** operation: `|Входы|≥1` and
`|Выходы|≥1`. The operator/ERP data feeds (`Инженер по планированию`,
warehouse register, ERP counters) enter through the storage/analytics groups and
are wired by flow links (T2.3), not as sensors here.

## Decision 1b — perimeter amendment (T2.3, 2026-10-11)

The T2.3 flow pass left four residual endpoints whose counterparty is outside the
authored scope (supplier terms, carrier offers) or in the **not-yet-authored**
procurement loop (Phase 2 `SLC_PROC`). To close §4.2 within the pilot they are
modelled as explicit boundary operations (plan §3 / ontology §4.6), rather than
dangling:

| Boundary | Op code | Direction | Entity | External counterparty |
|----------|---------|-----------|--------|-----------------------|
| sensor | `PLAN-03-01-05` | in | `УсловияПоставки` | поставщик (условия поставки) |
| sensor | `SL_PLAN-02-01-04` | in | `Уведомление@ПредложениеТК` | перевозчик (предложение ставки) |
| actor | `PLAN-03-02-06` | out | `РекомендацияПоЗапасам` | контур закупок (Phase 2) |
| actor | `PLAN-03-03-05` | out | `ПереченьНеликвидов` | реализация/списание |

Everything else in the two files remains internal; the full pilot graph is wired
by the per-file «Потоки (Flow Links)» tables (T0.7 Decision 4): internal edges on
identical `Type@State` tokens, cross-domain edges into existing
ENG/MNT/MFG/SL_LOG/ORG/HRP/ANLZ/STRAT operations, and these boundaries.

## Decision 2 — internal shared entities

The pilot exchanges only declared `Entity-State` types (T0.3 v0.2). New types
added for this vertical: see `T0.3` §"v0.2 — Planning & logistics additions".

Key shared types across the seam:

- `ПотребностьВРесурсах` — PLAN-01-02 → SL_PLAN-01-01 (`ПотребностьВРесурсах`)
  and SL_PLAN-01-02 (space planning).
- `РеестрЗаказов` — PLAN-01-01 → PLAN-01-02.
- `СменносуточноеЗадание` (+`@Проект`/`@Согласовано`) — PLAN-01-03 → MFG, ORG,
  PLAN-02.
- `НормативЗапаса` / `ТочкаЗаказа` / `СтраховойЗапас` / `ПараметрыЗапасов` —
  PLAN-03 ↔ SL_PLAN-01 seam (owner split, T0.1 D2 §3: PLAN-03 norms, SL_PLAN-01
  order point).
- `КлассификацияABCXYZ` — PLAN-03-02 and SL_PLAN-01-03 (both produced; downstream
  `РекомендацияПоЗапасам`).
- `ЛогистическиеОграничения` — SL_PLAN-03-01 → S&OP (PLAN).
