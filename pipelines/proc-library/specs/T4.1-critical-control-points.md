# T4.1 — Critical control points (КТК): derivation spec

Status: frozen · Phase 4 (T4.artifacts, sub-plan 02) · English (service doc)

Canonical source: umbrella `1791810263662-artifact-chain-ktk-priority-grid.md`
§5 (КТК derivation, row semantics, keystone rule). This spec makes that
derivation reproducible for the 10 `library/artifacts/КТК/<CODE>_КТК.md` files
and is the reference the author follows while porting the source `*_КТК.md`.

Format contract (frontmatter, heading, exact table header, cell vocabularies)
lives in `specs/T4.9-artifact-format.md`; the role register lives in
`specs/T4.0-role-archetypes.md` + `role_registry.json`. This spec adds only the
**derivation rules** — the mapping from the source КТК columns and the library
attributes to the unified КТК columns.

## 1. Purpose and shape

One file per canonical role (10 files). Each file answers: *which processes is
this role pivotal in, and how is that pivoting controlled?* A file carries at
most one role section (`## <Название> (<КОД>)`) and one КТК table per §T4.9.

## 2. Column → attribute mapping

Source column (uniform across all 10 source files) → unified КТК column:

| Source column | Unified column | Rule |
|---|---|---|
| № | `№` | renumbered 1..N after folding/deduplication |
| Критический процесс (группа, код) | `Код процесса` | the **library** process/subprocess code, literally (case-sensitive); a source label with no code (`OEE`, `РКК`, `Время ТС`, `КТК/СЦП`) is resolved to the library node that produces that result |
| Роль <роль> | `Роль` | see §3 |
| Критический выход (результат контроля) | `Критический выход` | from the source; may be re-anchored to the library `**Выходы:**` |
| Измеримый KPI / критерий | `KPI/критерий` | library `**КПЭ:**` wins where the library has one; a hard target is dropped or marked «ориентир» (umbrella §5) |
| Частота контроля | `Частота контроля` | source cadence, reconciled with the library `Периодичность` (§4) |
| Кто предоставляет данные | `Источник данных` | the producer's owner, mapped to a canonical role name |

Two columns are **derived**, not copied from the source:

- `keystone` — §5.
- `Критичность` — the aggregated library criticality of the node being
  controlled (§6).

## 3. `Роль` — precedence and granularity

The **library is authoritative**; the source wording is an input, not the
verdict:

1. If the canonical role is the row node's **direct** `**Владелец:**` (library
   owner) → `Владелец`. Do not let a *descendant* node's owner promote the row:
   the row points at one node, and its owner is that node's own owner.
2. Else if the canonical role appears as an operation `**Исполнитель:**` in the
   node or its descendants → `Участник`.
3. Else → `Косвенно`.

A source-supplied `Участник`/`Косвенно` is *kept* only when step 2 holds;
otherwise the row is re-evaluated and demoted to `Косвенно`. A source
`Владелец` that the library does not confirm is likewise re-evaluated.

**Granularity follows the source.** A row may point at a whole process (e.g.
`MNT-01-01`) or a group; the KТК sits where the *critical point* sits, so
subprocess-level rows are kept subprocess-level. Do not silently promote a
subprocess row to its parent process.

**Role resolution uses the full mapping tables** (`owner_synonyms`, `fold_map`,
`event_owner_map` of `role_registry.json`), so `ПЭО` → {РП, ГД}, `ИПП` → РП,
`ОТК` → РК, `РПС` → ГТ, `Эколог`/`Специалист по охране труда` → ГИ, etc. Workers
(`Оператор`, `Кладовщик`, …) never become owners.

## 4. `Частота контроля` and `Источник данных`

- Cadence is expressed in words matching the library `Периодичность` vocabulary
  (`shift < day < week < month < quarter < year`; `event` for triggered
  events). Where the source and the library disagree, the library wins.
- `Источник данных` names the canonical role that produces the data (fold
  `ПЭО`→Руководитель производства, `ИПП`→Руководитель производства,
  `ОТК`/`Представитель руководства по качеству`→Руководитель качества,
  `Менеджер по персоналу`→HR-менеджер, `Руководитель складского комплекса`→
  Руководитель склада (логистика), `РПС`→Главный технолог, `Эколог`→Главный
  инженер).

## 5. `keystone` rule

`keystone` is a **semantic judgment** — *"without it everything collapses"* —
not a mechanical flag. The library criticality is the **evidence**, not the
definition. A row is `да` only when **all** hold:

1. the role is the node's `Владелец` or an operation `Исполнитель`
   (umbrella §5; equivalently `Роль` ∈ {`Владелец`, `Участник`} in §3 terms),
2. the node carries ≥1 `high` operation **or** the point is a control/gate/
   bottleneck/SPOF, and
3. an explicit semantic review confirms the pivot (recorded in
   `Обоснование keystone`).

Otherwise `—`. `keystone` uses the literal values `да` / `—` (a plain `-`/`–`
is accepted by the checker as the empty marker).

## 6. `Критичность` — criticality-evidence rule

`Критичность` is the **aggregated library value** over the node the row points
at: the maximum of `**Критичность:**` across the node's operations
(`high > medium > low`). The aggregated value is what justifies §5.2. It must be
one of `high` / `medium` / `low` (H5).

## 7. `Обоснование keystone`

Required (non-empty) on every row with `keystone = да` (W5), and left empty on
`—` rows. It states the pivot in words — the control/gate/bottleneck/SPOF the
role owns and what collapses without it — and cites the evidence (the `high`
criticality of the named output). It is ported prose: never parsed except for
non-emptiness.

## 8. Folding (per role register)

- `ИПП` rows fold into **РП**; `ПЭО` rows fold into **ГД** and **РП**.
- After folding, drop exact duplicate `(role, process)` rows (W6).
- Result: exactly 10 files, one per register code, no orphan role.
