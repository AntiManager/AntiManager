# T0.4 — Goal attribute schema (means–end)

Status: draft · Phase 0 · English (service doc)

## Purpose

Define the goal attribute on every `ProcessNode` and the means–end validation
rule (plan §4). The goal spine is what makes the artifact chain (Phase 4)
derivable: КТК, КПЭ, priority matrix, event grid, profiles, КУ, ПС audit all key
off goals (plan §4).

## Decision 1 — reuse the regulated block

The library already carries a repeating regulated block at PROCESS and
SUBPROCESS level:

```
**Код:** …
**Владелец:** …
**Триггер:** …
**Цель:** …          ← goal (already present)
**КПЭ:** …
**Входы (из):** …
**Выходы (в):** …
```

The refactor **reuses** this block unchanged (no redesign) and adds two optional
attributes: `**Горизонт:**` (Decision 3) and `**APQC:**` (T0.2).

At OPERATION level the legacy format has `Исполнитель / Входы / Выходы / КПЭ`
and **no `Цель`** — that is the semantic gap. The refactor **adds
`- **Цель:** …`** to every operation.

## Decision 2 — goal on every node

| Level | Carrier | Required |
|-------|---------|----------|
| LIBRARY | `#` title block: `**Цель библиотеки:**` | yes (enterprise goal) |
| GROUP | `##` block: `**Цель группы:**` | yes |
| PROCESS | `**Цель:**` in the regulated block | yes |
| SUBPROCESS | `**Цель:**` in the regulated block | yes |
| OPERATION | `- **Цель:** …` bullet | yes |

Schema (all levels):

- `goal.text` — non-empty string (Russian, human-facing content).
- `goal.kpi` (`КПЭ`) — optional; measurements of the goal (plan §4).
- `goal.horizon` — optional enum, see Decision 3.
- `serves` — optional explicit pointer `- **Служит цели:** <ancestor code>` used
  when the contribution is not implied by the parent chain.

## Decision 3 — planning horizon (first-class dimension)

Planning horizons are a first-class dimension (plan §4/§9). `Горизонт` maps to
ontology `plans.horizon` / horizons L0–L4:

| `Горизонт` | ontology | planning meaning |
|-----------|----------|------------------|
| `year` | L0 | strategy |
| `quarter` | L1 | tactics |
| `month` | L2 | tactical-operational |
| `week` | L3 | operational |
| `shift` | L4 | operations / execution |
| `event` | — | triggered, no fixed horizon |

A node with no `Горизонт` is horizon-agnostic (acceptable). Planning is the
keystone seam (sales/S&OP → production → procurement/logistics), so PLAN /
SL_PLAN nodes should carry explicit horizons.

## Decision 4 — decomposition & validation rule

- **Decomposition rule:** a parent goal is decomposed into child goals; children
  collectively achieve the parent (plan §4).
- **Means–end validation (validator §7 extension):**
  1. every `ProcessNode` (GROUP, PROCESS, SUBPROCESS, OPERATION) has a non-empty
     `goal.text` → else `INVALID` (orphan node);
  2. the LIBRARY root has a goal → else `INVALID`;
  3. if a node declares `Служит цели: X`, then `X` must be an ancestor code →
     else `INVALID` (dangling goal link);
  4. a GROUP/PROCESS with no goal, or a node whose children exist but none of
     them can be reached from the parent goal chain structurally → `WARNING`.
- No orphan goals: a goal that is neither the library goal nor attached to a
  node is invalid.

## Worked chain (T0.4 verification target)

Adapted from ontology §12 (`QUAL-03-01`):

- GROUP `QUAL` — Цель группы: «Стабильное качество продукции, соответствующее
  требованиям и договорам».
- PROCESS `QUAL-03` — Цель: «Подтверждённое соответствие каждой партии сырья,
  материалов и продукции».
- SUBPROCESS `QUAL-03-01` — Цель: «Полный входной контроль сырья до запуска в
  производство».
- OPERATION `QUAL-03-01-01` — Цель: «Установить наличие/отсутствие сертификатов
  партии до начала контроля».

Chain check: each child goal contributes to the parent goal (means–end green);
horizons: GROUP `year`, PROCESS `month`, SUBPROCESS/OPERATION `shift`/`event`.
