# T4.8 — Artifact conformance: checks, severity and sign-off

Status: frozen · Phase 4 (T4.artifacts, sub-plan 05) · English (service doc)

Canonical source: umbrella `1791810263662-artifact-chain-ktk-priority-grid.md`
§5 (invariants), §6 (execution rules), §8 (total acceptance) and decision **D6**
(severity model). Implements the verification for the three artifacts under
`library/artifacts/`; the format they must conform to is `specs/T4.9`.
The checker is `check_artifacts.py`; it reuses `engine.py` (process/code
resolution) and `token_scan.py` (identity-token classes).

## 1. Purpose

Define every conformance check, its severity, and the **sign-off procedure** so
that a run is reproducible and no warning is ever silently waived.

## 2. Severity model (D6)

- **H\*** — *hard*. Mechanical or traceability invariants. A run is conformant
  only when `H\* = 0` (checker exit `0`).
- **W\*** — *warning*. Coverage/owner-consistency and semantic-plausibility
  judgments. Every `W\*` must be **fixed** or **explicitly waived with the
  product owner's sign-off** (§6). Warnings are advisory by design: a false one
  is a documented waiver, never a silent pass.

## 3. Hard checks (H1–H7)

| Id | Definition | Notes |
|----|------------|-------|
| H1 | Role sets are identical across the three artifact kinds and equal the register (10). | `H1a` = per-file: role codes ⊆ register and non-empty; `H1` = cross: union per kind == register. |
| H1b | Each recognized-kind artifact declares a `roles:` frontmatter key (T4.9 §2). | Presence only; the value is validated by `H1a`/`H1`. |
| H2 | Every referenced process code resolves to a library node. | Codes are literal, case-sensitive (`\b[A-Z][A-Z0-9_-]*-\d{2}(?:-\d{2})*\b`); `REG-<n>` excluded (H6). |
| H3 | Every grid event has a non-empty `Горизонт` from the vocabulary. | `{shift, day, week, month, quarter, year, event}`. |
| H4 | Each event's `Горизонт` matches its section cadence. | daily→{shift,day}, weekly→{week}, monthly→{month}, quarterly→{quarter}, yearly→{year}; an unrecognized section cadence raises a note and H4 is not applied to it. |
| H5 | Every КТК row has `keystone ∈ {да, —}` and `Критичность ∈ {high, medium, low}`. | `-`/`–` accepted as the empty marker. |
| H6 | Client + holding stop-word scan over artifacts = 0. | Artifact stop-words (УК, ПС ПП, …) live in the checker; identity classes from `token_scan.py`. One exception: a money figure on a line marked «ориентир». |
| H7 | Traceability: every row of every artifact references ≥1 valid process code. | A row with no code is a gap (gaps = 0). |

The base run always performs the **format-contract conformance** (T4.9 §2/§3/§4):
`artifact:` frontmatter recognized, `roles:` frontmatter present (H1b), exact table
header match, and role headings exactly `## <Название> (<КОД>)`. A file whose
frontmatter carries no recognized `artifact:` kind is ignored (T4.9 §1).

## 4. Warning checks (W1–W6)

| Id | Mode | Definition |
|----|------|------------|
| W1 | `--cross` | A role's `keystone = да` code should appear in that role's matrix section or grid (as an event owned by that role). |
| W2 | `--cross` | A grid event's `Процессы` codes should list that owner role as a library `Владелец`/`Исполнитель`. |
| W3 | `--semantic` | `Делегирование` non-empty for quadrants «Срочно, но не важно» / «Не срочно и не важно». |
| W4 | `--semantic` | Every numeric KPI marked «ориентир». |
| W5 | `--semantic` | Every `keystone = да` has a non-empty `Обоснование keystone`. |
| W6 | `--cross` | No duplicate `(role, process)` КТК rows. |

## 5. Modes, exit codes

```
python pipelines/proc-library/check_artifacts.py "<vault>"                 # H1-H7 + contract
python pipelines/proc-library/check_artifacts.py "<vault>" --cross         # + W1/W2/W6
python pipelines/proc-library/check_artifacts.py "<vault>" --semantic      # + W3/W4/W5
python pipelines/proc-library/check_artifacts.py "<vault>" --cross --semantic
python pipelines/proc-library/check_artifacts.py "<vault>" --json report.json
```

Exit `0` = no H-violation; `1` = H-violation(s); `2` = usage/IO error.

## 6. Sign-off procedure for waivers

A warning is resolved in exactly one of two ways, both recorded in the execution
log (`.kilo/plans/1791810263662-…-execution-log.md`):

1. **Fix** — the artifact or its generator is changed so the warning no longer
   fires; the checker is re-run and the warning is gone.
2. **Waiver** — the warning is correct but acceptable *by design*. The waiver
   must state the rule, the concrete instances, the rationale, and the
   approver. **The product owner (user) is the only approver.** A waiver without
   an owner sign-off is not a resolution and keeps the run open.

Reviewers do not sign their own waivers. The sign-off lives in the log as a
dated line: `W-sign-off <id> <instances> — approved by user (<date>)`.

## 7. Traceability report

The traceability report answers three links and reports gap counts:

- **role → КТК process → goal** (process goal from the library node);
- **matrix task → process**;
- **event → process + horizon**.

Acceptance: every link resolves, i.e. traceability gaps = 0 or explicitly
waived (same rule as H7).

## 8. Semantic review checklist

A human review of judgment quality, recorded in the log:

- [ ] keystone plausibility — each `да` is a genuine pivot (control/gate/
      bottleneck/SPOF), not merely a `high` process.
- [ ] keystone code↔meaning — for **every** keystone row, the `Критический выход`
      matches the authoritative library node name for that code. H2 only proves the
      code *resolves*; a valid code can still carry a drifted meaning (source
      taxonomy drift), so a structural pass cannot see it.
- [ ] quadrant logic — matrix tasks sit in the quadrant their urgency/importance
      imply.
- [ ] KPI plausibility — measures match the controlled output.
- [ ] no client drift — no client/holding wording (independently of H6).
- [ ] no cross-artifact contradiction — role/process/owner claims agree across
      КТК, matrix and grid.
